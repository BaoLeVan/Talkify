### 1.4 Tìm kiếm user — Logic ưu tiên

```
Input: q = "0901234567" hoặc "user@email.com" hoặc "tranthib"

┌─────────────────────────────────────────────────────────────────┐
│                   SEARCH PRIORITY CHAIN                          │
│                                                                  │
│  q có dạng số điện thoại?                                        │
│  ─────────────────────────                                       │
│  YES → SELECT * FROM users WHERE phone = q (EXACT)              │
│         ↓ nếu tìm thấy → trả về ngay                            │
│         ↓ nếu không → tiếp tục                                   │
│                                                                  │
│  q có dạng email (chứa @)?                                       │
│  ─────────────────────────                                       │
│  YES → SELECT * FROM users WHERE email = q (EXACT, case-insens) │
│         ↓ nếu tìm thấy → trả về ngay                            │
│         ↓ nếu không → tiếp tục                                   │
│                                                                  │
│  Còn lại → tìm theo username                                     │
│  ──────────────────────────                                      │
│  SELECT * FROM users                                             │
│  WHERE username ILIKE '%q%'                                      │
│     OR full_name ILIKE '%q%'                                     │
│  ORDER BY similarity(username, q) DESC                           │
│  LIMIT 20                                                        │
└─────────────────────────────────────────────────────────────────┘

Sau khi tìm thấy danh sách users:
→ Với mỗi user, join friendships để xác định friendshipStatus:
   NONE            → chưa có quan hệ
   PENDING_SENT    → mình đã gửi lời mời, chưa được phản hồi
   PENDING_RECEIVED→ có người gửi lời mời cho mình
   FRIEND          → đã kết bạn
   BLOCKED         → đã block hoặc bị block
```

### 2.3 Flow khi User B OFFLINE

```
                 Kafka Consumer (delivery)
                         │
                         │ HGET ws:sessions:userId-B
                         ▼
                    Redis: (nil)  ← User B OFFLINE
                         │
             ┌───────────┴────────────────┐
             │                            │
             ▼                            ▼
   INSERT pending_messages         FCM / APNs Push
   (MongoDB, TTL 30 ngày)

     recipientId: userId-B,
     payload: {...}
   }
             │                            │
             │                            ▼
             │                   User B receives push:
             │                   "Nguyễn Văn A: Xin chào!"
             │
             │ ─ ─ ─ ─ ─ User B kết nối lại ─ ─ ─ ─ ─ ─
             │
             ▼

### 2.4 Flow 3-Phase ACK (Sent → Delivered → Read)

```
Timeline:
─────────────────────────────────────────────────────────────────────▶

Client A                    Server                    Client B
   │                           │                          │
   │──── SEND(msg) ───────────▶│                          │
   │◀─── ACK {status:SENT} ────│    ① SENT                │
   │  [icon: ✓ (grey)]         │                          │
   │                           │──── NEW_MESSAGE ─────────▶│
   │                           │◀─── DELIVERY_ACK ─────────│
   │◀─── MESSAGE_DELIVERED ────│    ② DELIVERED            │
   │  [icon: ✓✓ (grey)]        │                          │
   │                           │                          │ (User B mở chat)
   │                           │◀─── READ{lastSeq:1501} ───│
   │◀─── MESSAGE_READ ─────────│    ③ READ                 │
   │  [icon: ✓✓ (blue)]        │                          │

State transitions:
  SENT       → serverMessageId đã được cấp, lưu vào Kafka
  DELIVERED  → message đã tới device của người nhận
  READ       → người nhận đã mở conversation và thấy tin nhắn

Redis ACK tracking (idempotency):
  SET dedup:msg:{clientMessageId} {serverMessageId} EX 86400
  (TTL 24h — tránh duplicate khi client retry)
```

### 2.5 Cross-instance Delivery qua Redis Pub/Sub

```
┌────────────────────────────────────────────────────────────────────────┐
│  User A (inst-1)                              User B (inst-3)          │
│       │                                              │                 │
│  SEND msg                                           WSS conn           │
│       │                                              │                 │
│       ▼                                              │                 │
│  inst-1:                                             │                 │
│  HGET ws:sessions:{userId-B}                         │                 │
│  → "inst-3:sess-xyz"                                 │                 │
│  PUBLISH ws:delivery:inst-3 <payload>                │                 │
│       │                                              │                 │
│       │         Redis Pub/Sub Bus                    │                 │
│       │─────────────────────────────────────────────▶│                │
│       │                                  inst-3:     │                 │
│       │                                  SUBSCRIBE   │                 │
│       │                                  ws:delivery:inst-3           │
│       │                                  → deserialize                 │
│       │                                  → SimpMessagingTemplate       │
│       │                                    .convertAndSendToUser(B)   │
│       │                                              │ push WS frame  │
│       │                                              ▼                 │
│       │                                         Client B              │
└────────────────────────────────────────────────────────────────────────┘

Redis Session Registry:
  HSET ws:sessions {userId}  "{instanceId}:{sessionId}"
  AUTO EXPIRE khi user disconnect (cleanup trong DisconnectHandler)

  ws:sessions:1001 → "inst-1:sess-abc"
  ws:sessions:1002 → "inst-3:sess-xyz"
  ws:sessions:1003 → nil  (offline)
```

### 2.6 Group Message Fan-out Strategy

```

                    │ Kafka Consumer│
                    │ (delivery)    │
                    └──────┬───────┘
                           │

### 2.7 Message Ordering Guarantee

```
Snowflake ID (global unique, time-sortable):
  ┌─────────┬──────────────────┬──────────┬──────────────┐
  │ 1 bit   │   41 bits        │ 10 bits  │   12 bits    │
  │ unused  │ timestamp (ms)   │ machineID│ sequence/ms  │
  └─────────┴──────────────────┴──────────┴──────────────┘

Sequence Number per Conversation (strict ordering):
  Redis: INCR seq:{conversationId}
  → Atomic, monotonically increasing trong mỗi conversation
  → Kafka partition key = conversationId → ordering đảm bảo

Client-side Gap Detection:
  messages.sort((a, b) => a.sequenceNumber - b.sequenceNumber)

  for (let i = 1; i < messages.length; i++) {
    if (messages[i].seq - messages[i-1].seq > 1) {
      // GAP detected! Request missing messages
      fetchMissing(convId, messages[i-1].seq, messages[i].seq)
    }
  }
```
